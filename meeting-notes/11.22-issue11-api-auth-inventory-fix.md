# 2026-11-22 — Issue #11: Server-side authentication on data endpoints + `/api/inventory` fix

**Branch:** `api-auth-inventory-fix-76045dd0`
**Audit baseline:** `main` @ `59b7e41`
**Audit IDs covered:** GEN-004, GEN-005 (partially — role checks deferred to D1), INV-004
**Notebook trace:** REQ-002, REQ-003, REQ-011; risks R-001, R-002, R-005; IT-005

## Problem

Two defects, both confirmed by inspection against `main`:

1. **No server-side auth (P0).** Every API endpoint accepted unauthenticated requests. `backend/app.py` never read the `Authorization` header, and `CORS(app)` was fully open — the only access control in the system was the client-side route guard in `AppLayout.jsx`, which enforces nothing at the layer that actually executes the operation. A plain `curl http://127.0.0.1:5000/api/inventory` returned data whenever Supabase was configured.
2. **Broken inventory endpoint.** `GET /api/inventory` queried table `Inventory` (`backend/app.py:182`), but the schema defines `inventory_items` (`supabase/migrations/20261024000000_initial_schema.sql:65`). Against the real database the endpoint 500s with PGRST205 (notebook integration test IT-005).

## Changes

### `backend/app.py`

- **`login_required` decorator (new).** Data endpoints now reject requests without credentials. It:
  - extracts the `Authorization: Bearer <token>` header — 401 if the header is missing, has no/mismatched scheme, or carries an empty token;
  - verifies the token by calling `supabase.auth.get_user(token)`, so signature, expiry and audience are all checked server-side by Supabase Auth — 401 (`"Invalid or expired token"`) on any rejection;
  - stores the authenticated user on `flask.g` so D1's role/permission checks can layer on top of this without re-verifying;
  - returns 503 if Supabase is not configured (consistent with existing endpoints).
- **Applied the decorator to `GET /api/inventory`.** `/api/health`, `/api/login` and `/api/signup` remain intentionally public, per the ticket.
- **Table name fix.** The inventory read now queries `inventory_items` (with a comment pointing at the migration for future readers).
- **CORS locked down.** `CORS(app)` (allow-everything) replaced with an origin allowlist from the new `CORS_ORIGINS` env var (comma-separated). Default is the Vite dev server: `http://localhost:5173,http://127.0.0.1:5173`. Origins not on the list get no `Access-Control-Allow-Origin` header and are rejected by the browser.

### `backend/.env.example`

- Documented `CORS_ORIGINS`.

### `backend/tests/test_inventory.py` (new, 10 tests)

- 401 on missing `Authorization` header
- 401 on malformed headers: empty, no scheme, wrong scheme (`Basic`), empty token, whitespace-only token
- 401 (`"Invalid or expired token"`) on a token Supabase rejects
- 200 with data on a valid token — and asserts the query targets `inventory_items`, not the old `Inventory` name
- 503 when Supabase is unconfigured
- `/api/health`, `/api/login`, `/api/signup` remain reachable without credentials
- CORS emits the allowlisted origin and nothing for an unlisted origin

## Design decision: `auth.get_user` vs local JWKS verification

`.env.example` already anticipated a `SUPABASE_JWKS_URL`, so local JWT verification (PyJWT + JWKS) was on the table. We chose `supabase.auth.get_user` instead because:

- no new dependencies (PyJWT, caching of JWKS, kid rotation handling) for a single-endpoint codebase;
- identical observable behavior (401 on missing/invalid/expired);
- the verification point (`flask.g.user`) is the same either way, so swapping in JWKS later is a drop-in change if per-request latency to Supabase becomes a concern.

## What is deliberately not in this change

- **Role-based checks (403)** — blocked on the permission matrix (issue D1). The decorator already exposes `g.user` for that work.
- **RLS policies** — the backend uses `service_role`, which bypasses RLS, so policies alone would not have fixed the API path (R-001 policy work builds on this).
